## Supabase: причина и подтверждение исправления

До настройки Storage сервер отвечал `NoSuchBucket / Bucket not found`; таблица `public.profiles` также возвращала `PGRST205`. Сам по себе публичный запрос не доказывает отсутствие закрытого bucket, поэтому реальная проверка проводилась через авторизованный интерфейс после настройки.

Подготовлен `supabase/INSTALL_LINAD_AVATARS.sql`: закрытый bucket `linad-avatars`, лимит 3 МБ, JPEG/PNG/WebP, политика доступа к папке собственного `auth.uid()`. Пользователь подтвердил выполнение SQL в проекте LINAD. [Правила доступа Supabase Storage](https://supabase.com/docs/guides/storage/security/access-control).

После этого в настоящем авторизованном браузере, без подмены API:

1. Иконка профиля открыла выбор файла, не переводя в настройки.
2. В Supabase загружен небольшой тестовый PNG с инициалами; получено подтверждение сохранения.
3. После перезагрузки страницы фото восстановилось из Supabase.
4. Через настройки фото успешно заменено: сохранён новый путь объекта.
5. Временное тестовое фото удалено через интерфейс; после перезагрузки снова показываются исходные инициалы.

Файлы изображения не записываются в Auth metadata. Там может сохраняться только путь объекта, используя существующую совместимость с аккаунтами до установки таблицы профилей. Проверка облачного учебного прогресса не входит в эту доработку.

Дополнительных настроек для загрузки фото в текущем проекте не требуется. При создании нового Supabase-проекта скрипт Storage нужно выполнить один раз; повторное выполнение безопасно. SQL не удаляет фотографии или данные профиля.
