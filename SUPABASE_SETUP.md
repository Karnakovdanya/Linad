## 1. Применить SQL

1. Войдите в [Supabase Dashboard](https://supabase.com/dashboard/project/agcvacclaebekvcblvod).
2. Откройте **SQL Editor → New query**.
3. Скопируйте **полностью** файл `supabase/migrations/202610200001_linad_accounts.sql`.
4. Нажмите **Run**. Скрипт выполняется в транзакции. При ошибке не запускайте отдельные фрагменты: сохраните текст ошибки для исправления.
5. В Table Editor проверьте таблицы `profiles`, `account_state`, `lesson_progress`, `module_progress`, `test_results`, `saved_words`, `favorite_tutors`.
6. На всех семи таблицах должен быть включён RLS и политика `own_records` для роли `authenticated`. У `anon` нет доступа.

`account_state` — полное состояние обучения для восстановления с другого устройства. Остальные таблицы — структурированные записи профиля, уроков, итоговых попыток, слов и избранного. Все они защищены RLS. RPC `linad_commit_account` выполняет атомарное сохранение и проверяет ревизию, сохраняя историю и объединяя конкурирующие изменения. Он работает как SECURITY INVOKER и получает владельца исключительно из `auth.uid()`.

Проверка SQL после установки:

```sql
select tablename, rowsecurity from pg_tables
where schemaname='public' and tablename in
('profiles','account_state','lesson_progress','module_progress','test_results','saved_words','favorite_tutors');

select tablename, policyname, roles, qual, with_check from pg_policies
where schemaname='public' and policyname='own_records';
```

Наличие RLS само по себе не заменяет проверку двумя тестовыми аккаунтами из пункта 5.

## 2. Настроить Auth для локальной разработки

В **Authentication → Sign In / Providers → Email** оставьте email/password включёнными. Google и Telegram не подключаются. Подтверждение email рекомендуется оставить включённым.

В **Authentication → URL Configuration**:

- **Site URL:** `http://127.0.0.1:5173/`
- **Redirect URLs**, добавьте каждую строку отдельно:

```text
http://127.0.0.1:5173/auth-callback.html?mode=confirm
http://127.0.0.1:5173/auth-callback.html?mode=recovery
http://localhost:5173/auth-callback.html?mode=confirm
http://localhost:5173/auth-callback.html?mode=recovery
```

Для ручной проверки production-сборки через `npm run preview` дополнительно:

```text
http://127.0.0.1:4173/auth-callback.html?mode=confirm
http://127.0.0.1:4173/auth-callback.html?mode=recovery
```

В email-шаблонах подтверждения и восстановления используйте стандартную ссылку **`{{ .ConfirmationURL }}`**. Не подменяйте её жёстко заданным `SiteURL`: Supabase должен сохранить переданный `redirect_to`.

Приложение использует PKCE. Открывайте письмо в том же браузере и на том же устройстве, где была запрошена ссылка. Если email подтвердился в другом браузере, войдите обычным email/паролем. Для восстановления запросите новую ссылку в нужном браузере. Обработчик удаляет код из адресной строки после обмена.

Для публичной регистрации проверьте **Authentication → Email / SMTP**. Встроенная отправка Supabase имеет ограничения по адресатам и частоте; для реальных пользователей настройте собственный SMTP и подтверждённый адрес отправителя. Web3Forms используется отдельно для заявок Tutors и не отправляет письма Supabase Auth. SMTP-пароль хранится только в Dashboard Supabase, никогда в `VITE_*`.

Официальные инструкции: [Password Auth](https://supabase.com/docs/guides/auth/passwords), [Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls), [PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow), [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

## 3. Запуск

```powershell
npm.cmd install
npm.cmd run dev
```

Откройте `http://127.0.0.1:5173/#/auth/register`.

Файл `.env.local` не публикуется в Git. Для новой среды скопируйте `.env.example` в `.env.local`. Обе переменные — публичная конфигурация браузера. Никогда не используйте вместо Publishable key ключ `service_role`, `sb_secret_*` или пароль базы.

После изменения переменных перезапустите Vite. При публикации переменные должны присутствовать во время `npm run build`: Vite встраивает значения в сборку.

## 4. GitHub Pages — после публикации

Сейчас не создавались репозиторий, workflow, remote или публичный адрес. Когда сайт будет опубликован:

1. Узнайте фактический адрес в **GitHub → repository → Settings → Pages**.
2. Укажите этот адрес с завершающим `/` в Supabase **Site URL**.
3. Добавьте к фактической базе сайта `auth-callback.html?mode=confirm` и `auth-callback.html?mode=recovery`, затем добавьте оба полных URL в Redirect URLs.
4. Сохраните локальные Redirect URLs, если локальная разработка продолжается.
5. Укажите `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` в среде сборки GitHub Actions. Это публичные значения; серверных секретов в workflow быть не должно.
6. Публикуйте весь `dist/`, включая `auth-callback.html` и `assets/account/auth-lake.png`.

Сохранены `HashRouter` и Vite `base: './'`. Внутренние страницы имеют вид `…/#/profile/words`, поэтому их перезагрузка не требует серверного rewrite. Email-ссылки приходят на настоящий статический `auth-callback.html`; он учитывает путь репозитория и возвращает управление HashRouter.

## 5. Ручная проверка действующего проекта

1. Зарегистрируйте собственный тестовый email, подтвердите письмо. До подтверждения интерфейс не должен показывать авторизованный кабинет.
2. Войдите, обновите страницу, проверьте сохранённую сессию и надпись «Профиль» в Header. Выйдите: надпись должна стать «Войти», кабинет недоступен гостю.
3. Запросите восстановление пароля, откройте письмо в исходном браузере и задайте новый пароль. Проверьте вход с ним.
4. До входа сохраните гостевое слово и выполните часть урока. После входа убедитесь, что гостевые записи **не импортируются автоматически**. Подтвердите объединение и дождитесь статуса «Данные синхронизированы». Гостевые записи остаются нетронутыми.
5. Сохраните слово из Practice, слово из лексики урока и Daniil Karnakov в избранное. Выполните задания/мини-тест. Открытие урока не должно делать его завершённым.
6. Войдите тем же аккаунтом в другом браузере/на другом устройстве: проверьте слова, избранное, прогресс, историю результатов и продолжение обучения.
7. Удалите слово, дождитесь синхронизации, откройте кабинет на другом устройстве. Удалённое слово не должно появиться снова. Между открытыми устройствами обновление выполняется при фокусе окна, возврате сети и каждые 30 секунд.
8. Создайте второй тестовый аккаунт. Убедитесь, что он не видит первый. В DevTools с токеном второго аккаунта запрос к таблице с `user_id` первого должен вернуть пустой результат; попытка записи с чужим `user_id` — ошибку RLS. **Не используйте SQL Editor под postgres для этой проверки: он обходит RLS.**
9. Отключите сеть, сохраните слово, проверьте сообщение об ошибке синхронизации. Включите сеть/нажмите «Повторить»: изменения должны сохраниться. Кеши разных аккаунтов раздельны. При выходе несинхронизированные записи остаются только в кеше соответствующего аккаунта до следующего входа на этом устройстве.
10. Проверьте RU/DE/EN, обе темы и мобильное меню. В настройках измените имя/пароль. Проверьте существующие уроки, Practice и заявки Web3Forms.

## Хранение и ограничения

- Гость: существующие `linad.levels.v1` и `linad.practice.v1`, без удаления старых данных.
- Аккаунт: изолированный кеш `linad.account.<user-id>.*`, защищённые облачные записи и Supabase-сессия.
- Удаление слов/избранного сохраняет отметку удаления для корректного объединения устройств.
- История попыток объединяется по стабильным данным попыток. Проценты обучения пересчитываются существующей логикой LINAD, а не берутся из демонстрационных значений макета.
- Резервные кеши остаются в localStorage. На общем компьютере используйте отдельный профиль браузера; выход не означает очистку кеша браузера.
- Проверка пароля и email выполняется Supabase. Сайт не хранит пароль пользователя в таблицах или логах.
- Нет OAuth, платных API, фиктивной синхронизации, новой системы платежей или изменений Web3Forms.
