# LINAD: первый модуль и администрация

## Статус

Клиентская реализация готова. Рабочая база Supabase не изменялась. Проверки браузера используют изолированный mock Supabase, а не аккаунты реальных пользователей. SQL дополнительно выполнен в изолированном PostgreSQL 18.6 (PGlite): 18 проверок функций, ролей, RLS, статистики и повторной установки прошли. В этом окружении Auth/Storage представлены тестовой схемой, без подключения к вашему проекту. Серверная миграция, политики и назначение владельца ещё требуют установки и проверки в вашем Supabase. До этого `/admin` закрыт, а не показывает фиктивную статистику.

**Важное ограничение учебных материалов:** сейчас полностью опубликованы пять уроков и итоговый тест первого модуля **немецкого A1**. Английский A1 содержит два пробных урока; остальные модули/уровни преимущественно являются планами. Свободный доступ к первому модулю реализован для каждой пары язык/уровень, но отсутствующий контент не создавался и не выдаётся за законченный курс. Поздравление требует существующего `moduleStatus.completed`: пять реально завершённых уроков и успешный итоговый тест. Наполнение остальных первых модулей — отдельная редакционная задача.

## Поведение посетителя

- Публичные страницы, выбор языка/уровня, программа и первый модуль остаются открытыми.
- Уроки, упражнения и итоговый тест первого опубликованного модуля доступны без регистрации.
- При его завершении появляется окно регистрации. Оно корректно восстанавливается после обновления; закрывается по Escape и удерживает клавиатурный фокус.
- Прямые адреса второго и последующих модулей, их уроков и экзаменов требуют входа. Уже существующая проверка настоящих результатов обучения сохранена.
- После входа пользователь возвращается к выбранному модулю. Внешние URL в адресе возврата не принимаются.
- Ситуации доступны для знакомства; сохранение гостя остаётся локальным. Пояснение со ссылкой входа отличает локальное сохранение от облачного. Гость не вызывает облачный commit.

## Как сохраняется результат

`linad.trial-transfers.v1` хранит области выбранных пробных модулей. Вход из закрытого последующего модуля тоже сохраняет выбранную пару язык/уровень, без присвоения учебных результатов. Перед отправкой регистрации/входа записывается ожидаемый email. После получения проверенной Auth-личности создаётся копия прогресса только этих модулей, привязанная к UUID аккаунта. Один лишь ответ `signUp.user` без сессии не считается подтверждённой личностью: Supabase может возвращать скрывающий существование аккаунта ответ.

В копию входят уроки, упражнения, попытки тестов, незавершённый итоговый тест и относящаяся к ним учебная активность. Слова, избранное и посторонняя гостевая история не переносятся без прежнего явного согласия. Они остаются доступны для ручного объединения в профиле. Профильные языки самооценки не назначаются автоматически.

Копия объединяется с кешем аккаунта и серверным документом через существующий CAS/RPC `linad_commit_account`; конфликт ревизий повторяет загрузку и объединение. Подтверждение переноса записывается только после успешного серверного commit. Уникальные ID попыток и прежние ключи упражнений предотвращают дубли. Исходные гостевые записи и резервная копия не удаляются; другой UUID не получает привязанный к первому аккаунту перенос. При офлайн-ошибке локальный результат доступен, а перенос ждёт повторной синхронизации.

**Email:** `auth-callback.html` работает и под префиксом репозитория GitHub Pages. Pending-прогресс и адрес возврата переживают перезагрузку и ожидание письма. PKCE-подтверждение требует исходного браузера/устройства; если письмо открыто на другом устройстве, подтвердите email и затем войдите на исходном, где сохранён результат. После первой успешной синхронизации прогресс доступен на других устройствах. Локальный гостевой результат невозможно автоматически получить на другом устройстве до первой авторизации и выгрузки. Основание: [Supabase PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow).

## Установка Supabase — вручную

1. Сделайте резервную копию БД средствами Supabase. Сначала рекомендуется staging/отдельный тестовый проект.
2. Выполните **только читающий** `supabase/CHECK_TRIAL_ADMIN.sql`. Он показывает колонки, RLS, политики, grants и существующие функции, без строк аккаунтов. Проверьте результат до миграции. Если нужна помощь, пришлите эти результаты, без токенов и секретов.
3. Проверьте предшествующие миграции: `202610200001_linad_accounts.sql`, `202610210001_profile_details.sql`, `202610210002_profile_goals.sql`. Установленный `INSTALL_LINAD_ACCOUNTS.sql` уже объединяет их. Не выполняйте старые установщики повторно вслепую при неизвестных изменениях схемы.
4. Убедитесь, что каждая из `profiles`, `account_state`, `lesson_progress`, `module_progress`, `test_results`, `saved_words`, `favorite_tutors` имеет RLS и доступ только к собственному `user_id = auth.uid()`. Не должно быть дополнительных разрешающих чтение чужих строк политик. Обнаруженные отклонения надо разобрать отдельно; новая миграция намеренно не уничтожает неизвестные политики.
5. Выполните новый файл **`supabase/migrations/202610210003_trial_admin.sql`** целиком. Он создаёт отдельную закрытую схему и функции. Не добавляйте `linad_private` в API → Exposed schemas. Клиентам не нужны Usage/Select/Insert/Update на эту схему или её таблицы.
6. Зарегистрируйте и подтвердите аккаунт владельца. В Supabase → Authentication → Users скопируйте его **UUID**. В **`supabase/GRANT_LINAD_OWNER.sql`** замените `OWNER_UUID_FROM_AUTH_USERS` на этот UUID, проверьте и выполните отдельно через SQL Editor. Без замены скрипт остановится. Сам установщик никому не выдаёт роль.
7. Обновите страницу профиля: ссылка «Администратор» появляется только после серверного `linad_is_admin()`. Адрес панели: `/#/admin` (с вашим префиксом репозитория).
8. В Authentication → URL Configuration задайте фактический Site URL и разрешённый Redirect URL `https://ВАШ-ХОСТ/ВАШ-РЕПОЗИТОРИЙ/auth-callback.html` с нужными параметрами confirm/recovery. Для локальной разработки сохраните адрес `http://127.0.0.1:5173/auth-callback.html`. Не придумывайте production-адрес до публикации. Сохраните включённое подтверждение email и действующие шаблоны писем.
9. Выполните **`supabase/VERIFY_TRIAL_ADMIN.sql`**: это транзакционная проверка чтения с временными ролями/JWT-sub и rollback. Нужны владелец и обычный тестовый пользователь. Проверяются отказ анониму, отказ обычному пользователю, закрытость таблицы ролей, отсутствие чужих строк в семи пользовательских таблицах и доступ владельца. Скрипт выводит только UUID тестовых субъектов, без профилей/паролей.
10. В тестовом проекте повторите реальные REST-запросы с JWT обычного пользователя: `linad_is_admin` → `false`, `linad_admin_dashboard` / `linad_admin_user` → отказ `42501`; выборка `profiles?user_id=eq.ЧУЖОЙ_UUID` и `account_state?user_id=eq.ЧУЖОЙ_UUID` → пустые данные. Попытка POST/PATCH чужого UUID должна быть запрещена RLS. Аноним не должен получать никакие пользовательские строки. Затем проверьте с JWT владельца. Не публикуйте JWT и не вставляйте secret/service keys в браузер или `.env` фронтенда.

Если схема отличается от исходных SQL, **нужны результаты шага 2**. Проверка каталогов в новом установщике не заменяет аудит уже существующих grants/политик. Автоматически ничего на рабочем Supabase не исполнялось.

## Безопасность администратора

- `linad_private.admin_members` содержит только UUID и дату назначения. Нет клиентских таблиц ролей, регистрации администратора, email-allowlist или роли из редактируемых `user_metadata`.
- `linad_is_admin()` использует серверный `auth.uid()`, закрытую таблицу членства и подтверждённый аккаунт.
- Оба RPC с административными данными повторно проверяют роль внутри функции. Изменение интерфейса/JS не отменяет эту проверку.
- SECURITY DEFINER используется только для чтения Auth/закрытой аналитики и ограниченной записи дня собственной активности. Все такие функции имеют фиксированный пустой `search_path`, полные имена объектов, отзыв PUBLIC/anon Execute и минимальные явные grants. Основание: [Supabase database functions](https://supabase.com/docs/guides/database/functions), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).
- Поиск связанными параметрами, длина до 200, пагинация 25 пользователей; фильтры языка/уровня и подтверждения email проверяются сервером. Поиск не формирует исполняемый SQL.
- Обычные политики пользовательских таблиц не расширяются. Роль не даёт владельцу обычное API-чтение всех таблиц; только ограниченные admin RPC возвращают необходимые поля.
- Панель показывает имя, email, регистрацию, подтверждение, выбранные языки самооценки, сводку модулей и попыток уроков. Не отдаёт Auth-токены, пароли, IP, user-agent, сохранённые слова, аватары или полный `account_state`. В браузере admin-ответы не сохраняются в localStorage.
- Панель только читает данные. Удаление пользователей, смена ролей и паролей в неё не добавлены. Отзыв роли владельцем: `delete from linad_private.admin_members where user_id = 'НУЖНЫЙ_UUID';` — отдельная осознанная операция в SQL Editor, не часть миграции.

## Что означают показатели

- Регистрации считаются по `auth.users.created_at`, без удалённых аккаунтов и без не-email анонимных субъектов. Сегодня — день UTC, 7/30 — скользящие интервалы регистрации.
- Активность: только новые учебные действия авторизованного пользователя, принятые сервером. Нет записи при простом просмотре профиля, скачивании облачного документа или импорте гостевой истории. Сервер сам назначает UUID/дату; клиент не может записать день другому человеку или задним числом. Максимум одна строка на человека в день UTC. Это подтверждает приём учебного действия, а не добросовестность решения задания.
- История не восстанавливается из `last_sign_in_at` или старых дат прогресса. Активность за 7/30 дней возвращает **null**, пока не прошёл соответствующий полный период с установки. Интерфейс показывает «Нет достоверных данных». После этого — число пользователей с принятыми событиями за текущий и предыдущие 6/29 дней UTC. Офлайн-действия, не доставленные как события, в эту метрику не входят.
- Пройденные уроки/модули и использование курсов берутся из нормализованных сводок существующего sync. Нет синхронизированной сводки/старый формат — **неизвестно**, а не придуманный ноль. Нулевой результат в существующей валидной сводке действительно означает, что завершений ещё нет. Число аккаунтов с данными показано отдельно.
- Оценивание курса и формула прогресса не изменены. Результаты пока присылает клиент: они не являются защищённой аттестацией. Личные уровни профиля явно названы самооценкой.

## Хранение аналитики

Хранятся только UUID, день, время получения первого события, язык и тип действия; нет свободного текста событий, IP или полной истории кликов. Данные удаляются каскадно при удалении Auth-пользователя. Доступ — только owner RPC.

Рекомендуемый срок хранения новых дневных событий — **90 дней**. После проверки включите расширение `pg_cron` в Dashboard и отдельно установите ежедневную задачу (не включена автоматически; не касается курсов/профилей):

```sql
select cron.schedule(
  'linad-learning-days-retention', '17 3 * * *',
  $$delete from linad_private.learning_days
    where activity_date < (now() at time zone 'UTC')::date - 90$$
);
```

Проверьте, нет ли задания с таким именем, прежде чем создавать повторное. Если pg_cron недоступен, планируйте эту же операцию через доверенный серверный scheduler; до настройки автоматическое ограничение срока **не работает**. Дату начала наблюдений в `analytics_settings` сохраняйте для корректного расчёта покрытия.

## Реальное ограничение содержимого на GitHub Pages

Текущая проверка входа — удобный сценарий продукта, **не защита размещённых в JS уроков**. Все учебные данные и ключи ответов, включённые в статический bundle, посетитель может скачать. Эту архитектуру нельзя сделать безопасной только скрытием кнопок, localStorage-флагом или React-маршрутом.

Для настоящего ограничения нужен отдельный этап:

1. Оставить в GitHub Pages только публичные метаданные программы и материалы первого модуля.
2. Перенести остальные материалы в Supabase `course_lessons`/закрытый Storage. На сервере разрешить anon только `module_number = 1`, остальное — пользователю с действительной сессией (и отдельным entitlement, если позднее появится платный доступ). RLS должен проверять это при каждом чтении.
3. Загружать уроки по JWT через Supabase API или Edge Function с проверкой JWT и собственными серверными правами. Убрать эти материалы и файлы из репозитория/bundle, иначе ограничение обходится скачиванием статики.
4. Для достоверных результатов держать ключи правильных ответов в закрытой серверной схеме; оценивать попытки серверной функцией, принимать ID задания и ответы, а не `completed: true`. Запись подтверждённого прогресса разрешить только серверной проверке, с идемпотентным ID попытки.
5. Секреты допускаются только в серверных настройках Supabase, никогда в `VITE_*`, GitHub Pages и исходниках. Клиент использует только publishable key и свою сессию.

Эта серверная переработка содержимого и оценивания не применялась: она потребовала бы изменения действующей доставки курсов, которую в этой задаче сохраняем.

## Ручная приёмка после установки

1. В чистом браузере открыть публичные разделы, выбрать немецкий A1, пройти упражнения пяти уроков и тест. 70% — нет поздравления о прохождении, 80%+ при завершённых уроках — окно регистрации.
2. Обновить страницу, закрыть/открыть маршрут; результат не теряется. Прямые ссылки на второй модуль/урок/экзамен запрашивают вход.
3. Зарегистрироваться, дождаться письма, обновить страницу до подтверждения. Подтвердить email и войти. Первый модуль завершён, повторно проходить его не нужно.
4. Повторить со входом существующего аккаунта с историей: история сохраняется, повторные вход/синхронизация не дублируют попытки.
5. Временно отключить сеть: результат остаётся локально. Восстановить сеть, повторить синхронизацию и открыть аккаунт на другом устройстве.
6. Войти другим аккаунтом на том же устройстве: автоматического получения переноса первого аккаунта нет; гостевые оригиналы сохранены отдельно.
7. Проверить ситуации: просмотр и локальные слова работают без аккаунта, облачные RPC требуют реальной сессии.
8. Проверить anon/обычный/admin доступ через UI и REST, поиск, фильтры, пагинацию и детали. Отсутствующие метрики — неизвестны. Проверить появление собственного дневного события после нового учебного действия и отсутствие события от просмотра профиля.
9. Повторить критические экраны в RU/DE/EN, светлой/тёмной теме и на телефоне.

Полный перечень файлов и результаты автоматических проверок: `TRIAL_ADMIN_REPORT.md`.
