# LINAD — подготовка GitHub Pages

Проект подготовлен для статического размещения. Репозиторий не создавался, push и публикация не выполнялись. SQL и рабочий Supabase не изменялись.

## Публикация пока выключена

В `.github/workflows/pages.yml` проверки запускаются для push/PR в `main` и вручную. Выдача прав Pages и шаг deploy допускаются только после успешных проверок, только из `main`, вне PR и при **Repository Variable `PAGES_PUBLISH_ENABLED=true`**.

Оставьте эту переменную отсутствующей либо `false`, пока отдельно не решите публиковать сайт. Не включайте её только ради проверки workflow. Дополнительно можно настроить обязательное ручное одобрение environment `github-pages` в GitHub.

## Переменные сборки

После самостоятельного создания репозитория откройте **Settings → Secrets and variables → Actions → Variables** и добавьте:

| Имя | Значение |
| --- | --- |
| `VITE_SUPABASE_URL` | HTTPS URL вашего проекта из `.env.example` или `.env.local` |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Только публичный ключ `sb_publishable_…` того же проекта |
| `PAGES_PUBLISH_ENABLED` | Пока `false` либо не создавать |

Две переменные Supabase нужны именно при сборке. GitHub Actions не получает локальный `.env.local`. Публичный ключ войдёт в JS — это предусмотрено Supabase; права пользователей обеспечиваются Auth/RLS. Не используйте `service_role`, `sb_secret_…`, пароль БД или SMTP. Они не нужны workflow.

`tools/check-public-env.mjs` останавливает CI при пропущенных значениях, приватном ключе, небезопасном URL или приватной переменной `VITE_*`. Значения ключей не печатаются. Локальная проверка:

```powershell
node --env-file=.env.local tools/check-public-env.mjs
npm.cmd run lint
npm.cmd run build
npm.cmd test
```

Workflow использует Node 24 и Windows/Chrome для совместимости с утверждёнными шрифтами и геометрическими фикстурами. Устанавливает зависимости через `npm ci`, браузер через Playwright и выполняет весь набор тестов без пропусков и `continue-on-error`. После проверок в Pages передаётся только `dist`; исходники, `.env` и QA в сайт не включаются. Actions закреплены на версиях commit SHA.

## Адреса и Supabase

Для репозитория `REPO` владельца `USER`:

- Сайт: `https://USER.github.io/REPO/`.
- Профиль: `https://USER.github.io/REPO/#/profile`.
- Обучение: `https://USER.github.io/REPO/#/learn`.
- Администратор: `https://USER.github.io/REPO/#/admin`.

Сохраняются `base: './'` и HashRouter: серверные rewrite не требуются. Адреса `/REPO/profile` и `/REPO/admin` без `#` не поддерживаются. Для собственного домена замените корневой адрес; не добавляйте выдуманный CNAME.

В Supabase → Authentication → URL Configuration владелец вручную задаёт фактический **Site URL** и разрешённые адреса:

```text
https://USER.github.io/REPO/auth-callback.html?mode=confirm
https://USER.github.io/REPO/auth-callback.html?mode=recovery
```

Оставьте нужные локальные адреса для разработки. Проверьте стандартные шаблоны ссылок подтверждения/восстановления, custom SMTP и отправителя. До настоящей проверки письма, входа, синхронизации, RLS и роли владельца на выбранном домене работа production Supabase не считается подтверждённой.

Рекомендуемые ручные проверки после отдельного решения о публикации:

1. Гость завершает первый модуль; приглашение регистрации переживает обновление.
2. Подтверждение email в исходном браузере возвращает в курс; результат переносится один раз и появляется после входа на другом устройстве.
3. Второй модуль требует входа; обычный аккаунт не получает админ-данные и чужой прогресс.
4. Подтверждённый владелец получает реальные показатели `/admin`; права назначаются отдельно через уже подготовленные SQL-инструкции, без service key в браузере.

Миграции повторно вслепую не запускайте. Для проверки прав уже есть `supabase/VERIFY_TRIAL_ADMIN.sql`; проверяйте UUID и выполняйте вручную по `TRIAL_ADMIN_SETUP.md`.

Текущая проверка регистрации — ограничение интерфейса: материалы находятся в публичном JS. Серверная защита содержимого последующих модулей потребовала бы отдельной серверной выдачи через Supabase. Эта подготовка её не добавляет.

## Что остаётся в Git

Сохраняются `src`, `public/assets`, `supabase`, `shared`, `tests`, конфигурации, JSON/text фикстуры и provenance из `qa`. Исключены зависимости, сборка, приватные `.env`, ключи, отчёты Playwright, тяжёлые QA-снимки/видео/архивы и исходные дублирующие delivery-пакеты `LINAD/`, `LINAD_CODEX_ASSETS_UPDATE/`. Ничего из этих папок не удалялось.

`.gitattributes` задаёт LF для текстовых файлов при будущем Git checkout и сохраняет изображения как бинарные файлы. Существующие файлы приложения в рабочей папке не переписывались; чистая копия с нормализованными переводами строк проверена отдельно.

Проверка исходных фото Tutors теперь использует сохранённые SHA-256 оригиналов в `tests/fixtures/tutor-photo-originals.json`; поэтому ей не нужна публикация дублирующего пакета картинок. Все используемые изображения остаются в `public/assets`.

## Обновлённые тесты

Исправлены прежние ожидания пяти пунктов хедера, старого Email, перехода гостя в профиль, локального открытия внешнего Telegram и сценария курса без окна регистрации. Контрольные суммы сравниваются с фиксированным снимком утверждённой версии от 22.10.2026 (`tests/fixtures/release-approved-sources.json`), а не с устаревшими границами отдельных этапов. Тесты сами снимок не обновляют. Отдельная проверка защищает весь перечень файлов приложения, SQL, материалов и изображений, включая добавление/удаление; текст допускает только различия перевода строк при Git checkout.

Добавлены проверки отключённого по умолчанию deploy, безопасных переменных, содержимого production-артефакта и настоящего статического сервера с префиксом репозитория, профилем, закрытой админ-панелью и callback. Никакие тесты не отключены.

## Когда владелец разрешит публикацию

1. Указать точный адрес репозитория/домена и подготовить Supabase Auth/SMTP.
2. Самостоятельно загрузить проект в GitHub после проверки списка добавляемых файлов.
3. Заполнить две публичные переменные и выполнить workflow с выключенным deploy.
4. Убедиться в успешных проверках, выбрать **Settings → Pages → GitHub Actions**.
5. Только после отдельного решения установить `PAGES_PUBLISH_ENABLED=true` и запустить workflow на `main`. Дальнейшие push в `main` будут публиковаться автоматически только после успешных проверок. Если основная ветка имеет другое имя, сначала согласованно обновить trigger и обе проверки `refs/heads/main`.
