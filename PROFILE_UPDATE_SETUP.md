# LINAD — настройка обновлённого кабинета

**Эта инструкция описывает предыдущий этап.** Для финального профиля и исправленного сохранения используйте [PROFILE_FINAL_SETUP.md](PROFILE_FINAL_SETUP.md): настройки могут сохраняться через Supabase Auth ещё до установки таблиц; полный SQL собран в один файл.

Состояние: 21 октября 2026. Проект `agcvacclaebekvcblvod`.

## Причина предупреждения

Реальный API возвращает `404`, код `PGRST205` (таблица отсутствует в schema cache) для запросов к `public.account_state` и `public.profiles`. В открытом авторизованном кабинете также воспроизведена ошибка схемы. Это не ошибка выбора темы или локального хранилища. Auth может работать независимо от пользовательских таблиц.

Publishable key не даёт права выполнять административный SQL. Миграции подготовлены, но агент не применял их к серверу. Без этого шага нельзя подтвердить облачное сохранение, загрузку фото на сервер или серверную изоляцию аккаунтов. Предупреждение о настоящем сбое остаётся небольшим уведомлением с кнопкой повтора; успешная синхронизация отдельную техническую плашку не показывает.

## Применение SQL

1. Откройте [SQL Editor проекта](https://supabase.com/dashboard/project/agcvacclaebekvcblvod/sql/new).
2. Скопируйте **целиком** `supabase/migrations/202610200001_linad_accounts.sql` в новый запрос и нажмите **Run**. Он создаёт семь таблиц, RLS, триггер профиля и RPC `linad_commit_account(bigint,jsonb,jsonb)`.
3. В новом запросе выполните **целиком** `supabase/migrations/202610210001_profile_details.sql`. Он расширяет профиль и создаёт закрытый bucket `linad-avatars` с политикой владельца.
4. При ошибке сохраните полный текст ошибки. Не запускайте случайные отдельные строки и не отключайте RLS.
5. Обе миграции допускают повторный запуск. Они не удаляют прогресс, слова, попытки и аккаунты. Они обновляют только указанные функции, ограничения и политики LINAD.
6. Вернитесь в LINAD, нажмите **Повторить**. Если ошибка остаётся, обновите страницу и проверьте SQL ниже.

Storage создаётся самим SQL: **Private**, максимум **3 МБ**, только **image/jpeg, image/png, image/webp**. Делать bucket публичным не нужно. Подпись ссылки на фото создаётся только после входа и действует один час. Файлы размещаются в папке `<auth.uid()>/`. Политика разрешает пользователю операции только в своей папке.

Проверка в SQL Editor после применения:

```sql
select tablename, rowsecurity from pg_tables
where schemaname='public' and tablename in
('profiles','account_state','lesson_progress','module_progress','test_results','saved_words','favorite_tutors');

select column_name, data_type from information_schema.columns
where table_schema='public' and table_name='profiles';

select tablename, policyname, roles, qual, with_check from pg_policies
where (schemaname='public' and policyname='own_records')
   or (schemaname='storage' and policyname='linad_avatar_owner');

select id, public, file_size_limit, allowed_mime_types from storage.buckets
where id='linad-avatars';

select to_regprocedure('public.linad_commit_account(bigint,jsonb,jsonb)');
```

Ожидается: семь таблиц с `rowsecurity=true`, поля `first_name`, `last_name`, `avatar_path`, `study_languages`, семь политик `own_records`, политика `linad_avatar_owner`, bucket с `public=false`, лимитом `3145728` и тремя MIME-типами, существующий RPC с тремя параметрами.

Если всё присутствует, но API по-прежнему сообщает о схеме:

```sql
notify pgrst, 'reload schema';
```

Не добавляйте `service_role` или административные ключи в `.env`, `VITE_*` или браузер. Используется ранее настроенный Publishable key. Auth Redirect URLs и GitHub Pages для этого обновления менять не требуется; исходная инструкция — `SUPABASE_SETUP.md`.

## Ручная проверка реального облака

1. Войдите в свой аккаунт. В настройках укажите имя и фамилию, сохраните; обновите страницу.
2. Выберите только English и свой уровень. На главной кабинета должна остаться одна языковая карточка. Добавьте Deutsch, измените/удалите его. Прогресс курсов при этом не меняется.
3. Загрузите JPEG/PNG/WebP до 3 МБ. Проверьте фото после перезагрузки, затем с другого устройства после входа в тот же аккаунт. Замените фото и удалите его: должны вернуться инициалы.
4. Сохраните слово из обучения. В «Моих словах» включайте/выключайте RU/DE/EN: хотя бы один остаётся. Поиск по скрытому переводу тоже должен находить слово. Эти же настройки видимости используются в Practice.
5. Выполните реальное задание и проверьте восстановление результата на другом устройстве. Гостевой прогресс переносится только после явного нажатия «Объединить данные».
6. Создайте второй тестовый аккаунт. Он не должен видеть имя, фото, слова, избранное или прогресс первого. Запрос чужого пути в Storage с сессией второго аккаунта должен быть отклонён; запрос чужого `user_id` к пользовательским таблицам не должен возвращать строки. Политики проверяются на сервере, а не только в интерфейсе.
7. Отключите сеть: изменения учебного прогресса остаются в кеше текущего аккаунта. Включите сеть и повторите синхронизацию; убедитесь, что записи сохранились. Не очищайте localStorage для устранения ошибок.
8. Регистрацию с двумя именами, подтверждение email и восстановление пароля проверьте настоящими письмами. Автотесты используют изолированную модель API и не доказывают доставку писем.

## Реализация и ограничения

- Персональные языки хранятся в `profiles.study_languages`, отдельно от состояния курсов в `account_state`.
- `first_name` и `last_name` сохраняются в Auth metadata при регистрации и в `profiles`. Старое единое имя сохраняется без угадывания фамилии.
- Последний успешно сохранённый профиль кешируется отдельно для каждого аккаунта. Ошибки обновления формы не выдают сообщение об успехе и сохраняют введённые поля.
- При замене фото старая ссылка меняется только после подтверждённой загрузки и сохранения профиля. При ошибке сохранения новый файл удаляется только после проверки, что сервер его не использует. Если состояние сервера неизвестно из-за сети, файл остаётся закрытым: это безопаснее удаления уже сохранённого изображения. Ошибка последующей уборки старого файла также может оставить неиспользуемый закрытый объект.
- Проверки интерфейса и синхронизации с моделью API автоматизированы. Выполнение миграций, реальная RLS/Storage, доставка Auth-писем и синхронизация между настоящими устройствами требуют описанной выше проверки после настройки.

Официальные материалы: [закрытые bucket и ограничения](https://supabase.com/docs/guides/storage/buckets/fundamentals), [Storage RLS](https://supabase.com/docs/guides/storage/security/access-control), [папки владельцев](https://supabase.com/docs/guides/storage/schema/helper-functions).

Локальная проверка SQL выполнена настоящим PostgreSQL через PGlite 0.5.11 с минимальными служебными схемами Supabase: `qa/profile-update/check-migrations.mjs`, результат — `qa/profile-update/sql-verification.json`. Проверены выполнение обеих миграций и их повторный запуск, триггер имён, валидация уровней, CAS-ревизии, сохранение истории, запрет чтения и записи чужих данных и пути аватаров. Это не проверка конфигурации действующего Supabase Storage HTTP API.
